# Hermes Agent Deep Dive & Kaioken Comparison

**Date:** 2026-08-22
**Sources examined:** `inspire/hermes-agent` (primary), `inspire/pi`, `inspire/opencode` (secondary), `cli/` (Kaioken, comparison target)
**Output:** `doc_her/hermes-deep-dive-and-kaioken-comparison.md`
**Method:** Direct source reading — entry points (`run_agent.py`, `cli.py`, `gateway/run.py`), the conversation loop (`agent/conversation_loop.py`, 8,418 lines), tool dispatch (`agent/tool_executor.py`, `tools/registry.py`), the self-improvement stack (`agent/background_review.py`, `agent/curator.py`, `tools/skill_ledger.py`), context management (`agent/turn_context.py`, `agent/turn_finalizer.py`, `docs/micro-compaction.md`), and the Kaioken agent core (`internal/agent/agent.go`, `compact.go`, `prune.go`, `tools.go`, `internal/daemon/`, `internal/prism/`).

---

## 1. Executive Summary

Hermes is a **Python personal-agent platform** organized around one idea: the agent core is a narrow waist, and capability lives at the edges (tools, skills, plugins, CLI commands). Its defining engineering constraints are (a) **per-conversation prompt caching is sacred** — the system prompt is byte-stable for a conversation's life, and (b) a **closed learning loop** — the agent writes skills, memory, and a user profile from its own experience, with a background curator pruning and consolidating them.

Kaioken is a **Go single binary** that pairs a chat agent with a deterministic knowledge engine (wiki/cards/skills generated by LLM passes but verified and refreshed incrementally). Where Hermes pushes intelligence into the loop at runtime, Kaioken precomputes knowledge at build time and keeps the runtime loop small, explicit, and approval-gated.

The one-sentence contrast: **Hermes is a runtime that learns while it works; Kaioken is a workbench that learns between sessions.**

### At a glance

| Dimension | Hermes (`inspire/hermes-agent`) | Kaioken (`cli/`) |
| :--- | :--- | :--- |
| Language / runtime | Python 3.10+, threads + asyncio | Go 1.24, goroutines + channels |
| Delivery | uv-installed package, ~65k LOC in top-level modules alone | Single static binary (~38 MB) |
| Frontends | CLI (prompt_toolkit TUI), gateway (20+ messaging platforms), Electron desktop, ACP, TUI-gateway | Bubble Tea TUI, `run` one-shot, HTTP daemon (desktop sidecar) |
| Agent loop | One 8.4k-line `run_conversation` state machine with ~30 recovery paths | ~140-line explicit `Run` loop with steering/follow-up queues |
| Tools | ~100 registered via plugin registry, toolsets, MCP, PTC sandbox | ~10 core tools + extension registry + MCP |
| Context mgmt | Threshold compression + opt-in micro-compaction (aux model) | Deterministic prune (free) + LLM compaction at loop top |
| Learning | Closed loop: memory nudges, skill synthesis, weekly curator, audit ledger | Session-distilled memory files, generated skills, incremental wiki |
| Persistence | SQLite state DB + JSONL transcripts + FTS5 search | `.kaioken/` markdown/YAML + state.json |
| Permissions | 4-tier approval + hardline command detection + rules | Ruleset (allow/deny/prefix) + TUI approval for state changes |

## 2. The Reference Set in One Paragraph Each

### Hermes (`inspire/hermes-agent`) — the self-improving platform agent
Python. One `AIAgent` class (`run_agent.py`, 9,206 lines) whose `__init__` forwards ~90 parameters to `agent/agent_init.py`. The real loop lives in `agent/conversation_loop.py::run_conversation` (8,418 lines). Around it: `agent/` (150 modules), `tools/` (~120 files), `gateway/` (31k-line `run.py` + 22 built-in platform adapters in `gateway/platforms/` + 22 more plugin platforms), `cron/`, `skills/` (bundled skill library), `plugins/` (first-party plugins), `acp_adapter/`, `tui_gateway/`, `web/` (desktop UI). Everything is wired through `tools/registry.py`, a central registration table with toolset grouping, availability `check_fn`s, and plugin shadow-protection.

### Pi (`inspire/pi`) — the lean TypeScript harness
A monorepo (`packages/agent`, `ai`, `coding-agent`, `tui`, ...). `packages/agent/src/agent-loop.ts` is the canonical minimal agent loop; `packages/coding-agent/src/core/tools/` holds a small tool surface (read/write/edit/bash/find/grep/ls) built on TypeBox schemas. Its `edit.ts` is a multi-hunk engine: an array of `{oldText, newText}` chunks, each required to be unique in the original file and non-overlapping, with unified-diff preview. An `output-accumulator.ts` bounds streaming tool output. Philosophy: few tools, strict contracts, no magic.

### OpenCode (`inspire/opencode`) — the Effect-TS server platform
TypeScript on Bun. All subsystems are Effect services (`packages/core/src/`, `packages/opencode/src/`): sessions, LLM transport, filesystem, LSP, MCP, permissions. `session/session.ts` defines typed session schemas; `server/server.ts` exposes a typed HTTP API; clients (TUI, web, desktop) attach over RPC. Tools live in `packages/opencode/src/tool/` (edit, read, bash, grep, task, plan, skill, code-mode...). Its distinguishing traits: structured concurrency via fibers, snapshot-backed file revert (`session/revert.ts`), and a durable session-input inbox (V2 session core) that separates prompt admission from model execution.

## 3. How Hermes Works (Primary Analysis)

### 3.1 Process topology

Hermes is not one program; it is a family of processes sharing one agent core:

```
                 ┌────────────────────────────────────────────┐
                 │                AIAgent core                │
                 │  run_agent.py + agent/* (loop, tools,      │
                 │  context, memory, skills, providers)       │
                 └──────┬─────────┬─────────┬─────────┬───────┘
                        │         │         │         │
        ┌───────────────┘         │         │         └───────────────┐
        v                         v         v                         v
  cli.py (TUI)          gateway/run.py   cron/scheduler.py      acp_adapter/
  prompt_toolkit        31k lines: 40+   file-locked tick()     ACP server for
  REPL, slash cmds      messaging        every 60s; spawns      editors (Zed etc.)
  local sessions        platform         one agent per job      tui_gateway/ (RPC
                        adapters, one    with its own session   host for the Electron
                        cached agent     + delivery target      desktop app)
                        per session key
```

Key facts from source:

- **The gateway caches agents per conversation.** `run_conversation` opens by resetting per-turn compression state precisely because "the gateway caches agents across user turns" (`conversation_loop.py:1820-1824`). One long-lived `AIAgent` serves many turns, so its cached system prompt and client objects are reused — this is what makes prompt caching pay off.
- **Cron runs inside the gateway** as a 60-second tick with a file lock (`cron/scheduler.py:1-8`), spawning ephemeral agents that inherit config and deliver results to any platform.
- **Subagents are full `AIAgent` instances** spawned by `tools/delegate_tool.py`, tracked in a registry with steer/interrupt handles (`steer_subagent`, `interrupt_subagent`), and durable dispatch records are persisted to SQLite (`tools/async_delegation.py`) so abandoned delegations can be recovered and completions re-delivered after a restart.

### 3.2 The turn: prologue, loop, finalizer

A user turn is split into three phases, each its own module:

**1. Prologue — `agent/turn_context.py::build_turn_context` (1,481 lines).**
Everything once-per-turn: safe-stdio install, rotated-session recovery, primary-runtime restore, auxiliary-client runtime binding, MCP tool refresh (explicitly scheduled here because it "only ever extends a fresh request prefix — it never mutates the cached prefix of an in-flight turn"), memory hydration, todo/nudge injection, system-prompt restore-or-build, preflight compression, the `pre_llm_call` plugin hook, external-memory prefetch, and crash-resilient persistence of the user message. It returns a `TurnContext` dataclass — the loop's entire input contract.

**2. The loop — `agent/conversation_loop.py::run_conversation`.**

```python
while (api_call_count < agent.max_iterations
       and agent.iteration_budget.remaining > 0) or agent._budget_grace_call:
```

Inside each iteration: pending-redirect drain, provider request assembly (per-provider adapters: Anthropic cache markers, Gemini schema transforms, Codex app-server transport, MoA multi-advisor aggregation), a retry state machine (`while retry_count < max_retries` at line 2814) covering rate limits, billing/entitlement errors, stale credentials (with a per-entry refresh tally so a single-entry OAuth pool can't spin forever), empty-response circuit breakers, and context-overflow handling; then tool-call parsing, canonicalization of arguments (`_canonicalize_tool_call_arguments` repairs corrupted JSON from weaker models), and dispatch into `agent/tool_executor.py` — which runs independent tool calls concurrently in a thread pool (`_max_workers_for_tool_batch`), applies authorization gates, pre/post plugin hooks, heartbeats, and output bounding (oversized results spill to disk with a reference stub).

The loop is famous internally for its recovery paths; a sample: length-continuation retries, truncated-tool-call retries, repetition-loop detection, content-policy blocked results, compression-deferred results, verification-gate holds (`_pending_verification_response` is preserved if a budget exhaustion would otherwise eat a held-back answer), and mid-turn compression with a `CompressionCommitFence` that makes compaction cancellable and atomic.

**3. Finalizer — `agent/turn_finalizer.py::finalize_turn`.**
Persists the transcript, runs post-turn memory review gating, optionally fires one micro-compaction pass (see 3.4), emits compaction status, and settles kanban/budget bookkeeping.

### 3.3 The system prompt and the cache discipline

`agent/system_prompt.py::build_system_prompt` is the clearest expression of Hermes' design values. The prompt is assembled once per session and cached on the agent; it is rebuilt only after compression. It is layered **in cache-optimal order**:

```
parts["stable"]    identity, guidance (SOUL.md), tool definitions   — never changes
parts["context"]   session-stable context files (AGENTS.md etc.)
parts["volatile"]  skills index, memory, USER profile, timestamp    — changes most,
                                                                     rendered last
```

The docstring states the rule plainly: for implicit longest-prefix backends, "the content most likely to change is rendered last, so when the prompt is rebuilt the unchanged stable scaffold ahead of the change stays in the reused prefix." A `reconstruct_static_prefix` helper can re-derive the stable tier for a stored prompt, but only if the stored prompt **literally starts with** the rebuilt bytes — "never a rewritten prompt." This is a deliberate, enforced invariant (the AGENTS.md calls it "sacred"), and nearly everything else — MCP refresh timing, toolset freezing, compression keep-prompt paths — is arranged around it.

### 3.4 Context management: threshold + micro-compaction

- **Batch compression (default):** when token estimates cross a threshold, an auxiliary model summarizes the middle of the transcript; a `CompressionCommitFence` guards the commit so a concurrent interrupt can't tear it. Compression attempts are capped (`max_compression_attempts`, default 3) and only "rearm" after a provider response confirms the prompt is actually below threshold.
- **Micro-compaction (opt-in, `compression.micro_compact: true`):** after each completed turn, `finalize_turn` absorbs **one exchange** (an assistant turn plus its tool results) into a running summary. The design doc (`docs/micro-compaction.md`) records two principled choices: user messages are **never** compacted ("your prompts stay verbatim... paraphrasing an instruction into a summary is exactly how an agent ends up confidently doing the thing you told it not to, six turns later"), and the feature trades prompt-cache prefix stability for a smaller sawtooth — a tradeoff the docs tell you to price before enabling.

### 3.5 Tools: the registry and the footprint ladder

`tools/registry.py` is the single source of truth. Each tool module calls `registry.register(name, toolset, schema, handler, check_fn, ...)` at import time. The registry enforces:

- **Toolset grouping** (`toolsets.py`): `_HERMES_CORE_TOOLS` (web, terminal+process, file ops, vision, skills, browser, ...) shared by CLI and all platforms; scenario toolsets compose from others.
- **Availability gating:** `check_fn` per toolset classifies a toolset as lazy-init vs disabled (e.g., desktop UI tools only load when the session source is the desktop app — "never keyed on a process env var").
- **Shadow protection:** a plugin registering a name that collides across toolsets is rejected unless it passes `override=True` **and** the operator has opted in via `allow_tool_override` in config — raising `PermissionError` otherwise.
- **Bounded errors:** every tool error body is truncated at 2,048 chars for the model (8 KB for logs) at the dispatch boundary, so no tool can stack unbounded error text into context.

`model_tools.py` computes the per-request tool schema list (cached, invalidated deliberately), coerces tool-call arguments against schemas, and observes results. The contribution rubric in AGENTS.md ranks new capability: extend existing tool → CLI command + skill → service-gated tool → plugin → MCP → new core tool **last**, because every core tool ships on every API call.

**Programmatic tool calling (PTC)** is the flagship extension: `tools/code_execution_tool.py` generates a `hermes_tools.py` stub module exposing only sandbox-allowed, currently-enabled tools as Python functions, runs the model's Python script in a sandbox, and services each `hermes_tools.tool(...)` call over a UDS RPC (local) or file-based RPC (remote backends) back into the parent's tool executor. Convenience helpers (`json_parse`, `shell_quote`, `retry`) are embedded in the stub. This collapses N tool round-trips into one zero-context-cost turn.

### 3.6 The learning loop

This is Hermes' differentiator. Four cooperating subsystems:

1. **Memory** (`tools/memory_tool.py`, `agent/memory_manager.py`). A `MemoryStore` with per-target files (`MEMORY.md`, `USER.md`) under `~/.hermes/memory/`, file-locked, drift-detected (a `.bak` comparison catches external edits), with consolidation-failure tracking. Memory is injected in the volatile tier of the system prompt and reloaded from disk on invalidation. The agent is nudged at intervals to persist durable facts.

2. **Skills** (`tools/skills_tool.py`, `skills/` library, agentskills.io-compatible). `skill_view` loads full content (the rubric explicitly forbids offset/limit pagination on instructional tools — "models will read page 1 and skip the rest"). `skill_manage` lets the agent create and edit skills at runtime. Skill readiness machinery checks frontmatter prerequisites and required env vars, with secret capture for setup.

3. **Background review** (`agent/background_review.py`). After complex turns, a review agent forks on the transcript digest with prompts engineered to extract *class-level* lessons ("skills capture 'how to do this class of task for this user'"), writing new/improved skills. It is cancellable when a live turn starts (`cancel_background_review_for_live_turn`).

4. **Curator** (`agent/curator.py`, `curator_backup.py`, `tools/skill_ledger.py`). A weekly-ish lifecycle: skills move active → stale → archived based on usage; consolidation merges overlapping skills; `prune_builtins` can retire shipped skills. Every mutation — by curator, agent, or user — appends a JSONL entry to `~/.hermes/skills/.curator_ledger.jsonl` with content-addressed before/after blobs, enabling `hermes curator rollback <entry-id>`. The ledger is "TELEMETRY, NOT A GATE" — a ledger failure never blocks the mutation it records. The curator's invariant: never hard-delete autonomously.

Supporting cast: `agent/learning_graph.py` builds a skill graph with usage stats and related-skill edges; `agent/insights.py` produces cost/usage reports from the session DB; `hermes_state_search.py` provides FTS5 (with a native CJK tokenizer in `native/fts5_cjk`) over past sessions.

### 3.7 Execution environments and safety

- **Seven terminal backends** (`tools/environments/`): local, Docker, SSH, Singularity, Modal, Daytona, Vercel Sandbox — one `EnvironmentBackend` ABC with a spawn-per-call model: a session snapshot (env, functions, aliases) is re-sourced before each `bash -c`; CWD persists via in-band markers (remote) or a temp file (local). `EnvironmentConnectionError` is distinguished from command failure so the model gets a "degraded, retryable" signal rather than a traceback.
- **File tools resolve paths per task** against an authoritative workspace root with sentinel-free absolute-CWD handling and container/host path mapping (`tools/file_tools.py`).
- **Approvals** (`tools/approval.py`): context-aware (interactive CLI, gateway, cron, single-query) with hardline command detection (`detect_hardline_command`), sudo stdin guards, and hook points. Subagents get auto-approve/auto-deny policies.
- **Browser**: a persistent `CDPSupervisor` per task holds one WebSocket to the browser, subscribing to Page/Runtime/Target events; its dialog/frame state merges into `browser_snapshot` results. A `browser-use` backend can replace the whole tool family.

### 3.8 Strengths and limitations (Hermes)

**Strengths**
1. **The learning loop is real, auditable, and safe.** Nudge → review fork → skill write → ledger → curator lifecycle, with rollback and a never-hard-delete invariant. No other agent in the reference set (or the wider ecosystem) closes this loop.
2. **Cache discipline as a first-class constraint.** The layered, byte-stable system prompt and MCP-refresh timing show measurable cost engineering, not folklore.
3. **Operational depth.** Retry/failover/credential-pool/billing/entitlement handling across ~15 provider modes is the difference between a demo and something that runs unattended on a $5 VPS.
4. **PTC** turns multi-step tool pipelines into single turns — a genuine context-economy win.
5. **Surface breadth with a narrow waist.** 40+ messaging platforms, 7 execution backends, desktop/TUI/ACP — all sharing one core, extended via plugins/skills rather than core growth.

**Limitations**
1. **Scale hotspots.** `cli.py` (21k), `gateway/run.py` (31k), `conversation_loop.py` (8.4k) are god-files mid-refactor (the rubric celebrates extracting them, which concedes they exist). The loop's ~30 interleaved recovery concerns make behavior hard to predict or unit-test in isolation.
2. **Python runtime cost.** Import tree, memory footprint, and startup latency are far from a compiled binary; the Windows story needs a bundled portable Git Bash to be workable.
3. **Concurrency model is mixed.** Threads + asyncio + subprocess + ContextVars coexist; correctness depends on discipline (e.g., the RPC stub's `_call_lock` exists because the protocol has no request IDs and would race).
4. **Complexity is the architecture.** The same features that make it powerful (compression fences, static-prefix reconstruction, MoA rebasing) create long-tail bug classes the issue tracker (five-digit issue numbers) reflects.
5. **Global mutable agent state.** Dozens of `agent._underscore` fields reset per turn are the loop's real control flow — fragile under refactoring.

## 4. Kaioken: The Comparison Target

### 4.1 Architecture

Single Go module; dependency flow is inward: `cmd`/`tui` → `agent`/`wiki`/`llm`/`daemon` → utilities (`scan`, `plan`, `codemap`, `state`, `skills`, `prism`, `gitx`). ~50 packages under `internal/`. Two natures:

- **Chat agent** — `internal/agent`: the `Run` loop, tool registry/executor, permission rulesets, context tracking, compaction, delegation, events bus.
- **Knowledge engine** — `internal/wiki` (brief → outline → passes → polish → verify → provenance), `internal/scan`/`codemap` (repo indexing), `internal/skills` (generated task guides), `internal/memory` (project/user memory files with jaccard dedup, reinforcement, digest), `internal/prism` (agentic retrieval: classify → decompose → retrieve → grade → interleave).

Frontends: Bubble Tea TUI (`internal/tui`), one-shot `run`, and an HTTP daemon (`internal/daemon`, 38 files) that the desktop app (Tauri, planned) drives as a sidecar, with SSE streaming, session CRUD, workspace handlers, and browser/research/PRISM endpoints.

### 4.2 Execution flow (from `internal/agent/agent.go::Run`)

```
Run(ctx, history)
 ├─ PRISM mode? inject grounded knowledge context for the prompt
 ├─ ApplyReminders(history, mode)          ← constraints restated against the prompt
 └─ for i, spent := 0, 0; ; i++            ← two counters: turns vs. billed steps
     ├─ manageContext()                    ← prune/compact BEFORE the request
     ├─ Budget.Check(SpendUSD())           ← refuse the spend, don't report it
     ├─ BeforeProviderRequest hook (bus)   ← prune/redact/annotate in place
     ├─ chatWithRetry()                    ← provider call
     ├─ Context.Record(tokens, len)        ← anchor measurement at provider truth
     ├─ runToolCalls()                     ← approval-gated execution
     ├─ drainSteering()? → append, continue (turn NOT billed)
     ├─ len(msg.ToolCalls) > 0? → spent++, continue
     └─ drainFollowUps()? → append, continue (not billed) : return
```

Design decisions worth naming:

- **Compaction only splits on a user-message boundary** (`splitForCompaction`) and runs **before** the request — "overflow is not recoverable in place... the reduction has to happen while the failure is still hypothetical."
- **Steering/follow-ups are unbilled**, with `maxTurns = 4 * steps` as an anti-flood ceiling so a hostile front-end can't steer forever.
- **Budget is enforced pre-call** with a warning injected as a context update so the model economizes for the rest of the session.
- **Events bus** (`events.Bus`) decouples the loop from TUI/daemon rendering, including a `BeforeProviderRequest` hook.

### 4.3 Tools, approvals, and knowledge

- **Tools** (`internal/agent/tools.go`, ~1,200 lines): read_file (numbered lines, binary detection), write_file, edit_file (multi-hunk `{path, old, new}` with `verifyUnchanged` optimistic concurrency and preview), search, list, run_command (timeout, output capture) — plus a `RegisteredTool` registry for extensions (`ext`) and MCP.
- **Permissions** (`internal/agent/permission.go`): ordered rules with wildcard targets, shell-operator awareness, command-prefix matching, chainable-command detection; the TUI approval modal is the hard gate for anything state-changing (AGENTS.md: "the agent will not make any state-changing modifications without explicit user approval").
- **Knowledge engine**: `kaioken wiki`/`update` run multi-pass LLM generation with a verify pass and provenance tracking; `update` uses `gitx.Changes` to regenerate only affected docs. `export` flattens cards/wiki/skills into AGENTS.md/CLAUDE.md/.cursorrules with zero LLM calls. `prism_turn` injects retrieved knowledge at turn start when in PRISM mode.
- **Memory**: markdown files with deterministic append, duplicate detection (jaccard over word sets), reinforcement counters, and session digest — deliberately simple, inspectable, and diff-friendly.

### 4.4 Strengths and limitations (Kaioken)

**Strengths**
1. **A single static binary**: instant startup, trivial install/update (`selfupdate`), no runtime deps — the direct opposite of the Python stack.
2. **The loop is readable.** ~140 lines express the whole policy: budgets, steering semantics, compaction timing, billing rules. A new engineer can hold it in their head.
3. **Deterministic context control.** Prune is free and predictable; compaction is a deliberate split at a safe boundary; token accounting anchors on provider-reported figures.
4. **Knowledge as build artifact.** The wiki/cards/skills pipeline is verified and provenance-tracked, refreshed incrementally from git — cheap at runtime, auditable on disk.
5. **Approval-first safety** with a real ruleset engine, not just a modal.
6. **Real cost guardrails** (OpenRouter usage accounting → hard stops) built into the loop.

**Limitations**
1. **No runtime learning loop.** Skills/memory are generated on command or distilled at session end; nothing nudges the agent mid-work to persist a lesson, and no curator prunes stale knowledge.
2. **Single-user, local-first.** No messaging-platform gateway, no cron, no remote execution backends; the daemon is a localhost sidecar.
3. **Smaller tool surface.** No browser automation, vision, PTC/code-execution sandbox, or subagent steering; delegation exists but is simpler than Hermes' durable dispatch.
4. **Provider surface is narrower** (OpenRouter/Anthropic/local), without Hermes' per-provider adapter zoo and failover chains.
5. **Context management is threshold-based only** — no micro-compaction equivalent, and compaction is LLM-summarization rather than a bounded amortized process.
6. **Windows-first quirks**: process handling is split `proc_unix.go`/`proc_windows.go`; terminal-empty detection and PTY workarounds are ongoing maintenance.

## 5. Head-to-Head: Hermes vs Kaioken

### 5.1 Architecture

| Aspect | Hermes | Kaioken |
| :--- | :--- | :--- |
| Core abstraction | One god-class `AIAgent` + 150 helper modules; behavior spread across per-turn resets of instance state | One small `Agent` struct; behavior explicit in the `Run` loop and its callees |
| Extension model | Footprint ladder: skill → CLI+skill → service-gated tool → plugin → MCP → core tool; plugin registry with shadow protection | RegisteredTool registry for extensions + MCP; skills are generated files, not runtime capabilities |
| Frontend coupling | Gateway owns sessions; CLI/TUI/desktop/ACP are thin clients over cached agents | TUI and daemon both embed the agent directly; events bus decouples rendering |
| State | SQLite DB (sessions, FTS5, delegations) + JSONL transcripts + ledger | `.kaioken/` tree: markdown/YAML artifacts + state.json |
| Concurrency | Threads + asyncio + subprocess pools + ContextVars | Goroutines + channels; events bus; context.Context cancellation |

The philosophical difference is **where intelligence lives**. Hermes puts it in the loop: the agent decides at runtime what to remember, which skill to write, when to compress. Kaioken puts it in the build: the knowledge engine precomputes verified context, and the loop stays a small deterministic machine. Hermes' approach adapts continuously but is expensive and complex; Kaioken's is cheap, predictable, and inspectable but static between runs.

### 5.2 Execution flow

| Phase | Hermes | Kaioken |
| :--- | :--- | :--- |
| Turn setup | `build_turn_context`: ~15 concerns (MCP refresh, memory hydration, prompt restore, preflight compression, plugin hooks, crash-safe persist) | `ApplyReminders` + optional PRISM injection — two calls |
| Provider call | Adapter matrix (Anthropic/Gemini/Codex/MoA/OpenRouter), retry state machine with credential pools, billing gates | `chatWithRetry` over one client abstraction; OpenRouter usage accounting |
| Tool exec | Thread-pool concurrency, authorization gates, plugin hooks, output spilling, PTC sandbox | Sequential `runToolCalls` with per-tool approval; `verifyUnchanged` on edits |
| Recovery | ~30 paths: empty-response breakers, repetition detection, length continuation, compression fences, verification holds | Retry with backoff; compaction pre-empt; budget stop; steering refund |
| Turn end | `finalize_turn`: persist, memory-review gate, micro-compaction, status | Persist via daemon/TUI; session distill on exit |

Hermes' flow is a state machine for surviving the real world (bad models, dead credentials, full contexts, interrupted compactions). Kaioken's flow is a contract: pre-call reduction, pre-call budgeting, unbilled steering, bounded turns. Hermes will degrade gracefully in chaos; Kaioken will fail loudly and legibly.

### 5.3 What each does that the other can't

**Hermes-only:**
- Closed learning loop (background review → skill synthesis → curator lifecycle → rollback ledger)
- PTC: model-written Python calling tools over RPC in one turn
- Messaging gateway (40+ platforms) + cron with delivery + voice/TTS + wake words
- 7 execution backends including serverless (Modal/Daytona) with hibernation
- Micro-compaction and MoA (multi-advisor) orchestration
- Cross-session recall via FTS5 (with CJK tokenizer) + session insights

**Kaioken-only:**
- Single-binary distribution with self-update
- Verified, provenance-tracked generated documentation (wiki verify pass, staleness tracking, incremental git-driven updates)
- Export-to-rules pipeline (AGENTS.md/CLAUDE.md/.cursorrules) with zero LLM cost
- PRISM agentic retrieval as a first-class mode (classify → decompose → grade → interleave)
- Deterministic prune that costs zero tokens
- Approval rulesets with shell-operator/chainable-command awareness as a first-class engine

### 5.4 Transferable ideas (both directions)

**Into Kaioken (highest value first):**
1. **The cache-stable layered system prompt.** Kaioken already regenerates reminders per turn; ordering stable→volatile and freezing tool lists mid-session would cut cost on OpenRouter immediately.
2. **A skill ledger + curator lifecycle.** Kaioken generates skills but never retires them. A JSONL audit + active/stale/archived transitions (even a simple cron-less "on update" pass) would keep `.kaioken/skills/` trustworthy.
3. **Mid-turn memory nudges.** A cheap counter-based gate ("every N turns, ask: is there a durable fact worth persisting?") is most of Hermes' learning value at a fraction of the machinery.
4. **Bounded tool-error bodies at the dispatch boundary** (Hermes' 2 KB cap) — one-line protection against context stacking.
5. **Durable delegation records.** Kaioken's daemon could persist dispatch/completion records so a restarted desktop app recovers subagent results.

**Into Hermes (if its maintainers wanted them):**
1. **Pre-call compaction.** Kaioken reduces context *before* the request because overflow is unrecoverable afterward — a cleaner invariant than retry-then-compress.
2. **Unbilled steering semantics** with an explicit anti-flood ceiling — a crisp policy worth stealing for the gateway.
3. **Deterministic prune before LLM compaction** — free token reduction ahead of the summarizer.
4. **The knowledge-engine verify/provenance pass** — generated docs with citations would slot into Hermes' skill system naturally.

---

## 6. Verdict

Hermes and Kaioken are answers to different questions. Hermes asks *"how should a personal agent that lives with you for months behave?"* and answers with a learning loop, a platform, and an obsessive cost discipline — accepting god-files, a heavy runtime, and long-tail complexity as the price. Kaioken asks *"how should a coding assistant for a repository behave?"* and answers with a fast deterministic core plus a build-time knowledge engine — accepting a static learning profile and a local-only surface as the price.

For Kaioken's roadmap, the highest-leverage imports from Hermes are not the platform features but the three disciplines: **cache-stable prompt layering**, **the audited skill lifecycle**, and **bounded everything at tool boundaries**. They improve cost, trust, and context hygiene without importing any of the complexity that makes Hermes hard to hold in one head.
